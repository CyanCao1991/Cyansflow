# BP测试用例质量审查（cyancao-bptestcase-review）

> **一句话定位**：与其说"测试覆盖了100%的代码路径"，不如说"测试覆盖了100%的业务风险"。

## 触发条件

当用户说以下内容时，**必须**先读此SKILL：
- "帮我看看这个测试方案" / "评审测试用例" / "review test case" / "review test plan"
- "这个测试覆盖全了吗" / "测这些够不够"
- 任何涉及IT系统测试用例/测试方案质量评估的请求

**不触发**：如果用户只是问"这个bug怎么复现"、"这个环境怎么搭"、"测试流程怎么走"，那是操作问题，不是测试用例审查。

## 核心哲学：三层测试价值模型

```
第1层：功能覆盖（最基础）
  └─ 每个功能点是否都有正向/反向用例？
  
第2层：业务场景（核心）
  └─ 真实业务流是否完整跑通？（非单接口/单页面验证）
  
第3层：风险覆盖（高阶）
  └─ 边界、异常、数据一致性、并发、安全、回滚是否覆盖？
```

**核心判据**：一个好的测试用例集，应该能回答"如果这个系统上线后出了大问题，我们的测试为什么没有发现它？"

## 14维审查框架

### 维度1：业务价值验证 🔴 P0

| 检查项 | 说明 |
|--------|------|
| 测试是否关联到具体业务场景 | 不是"测登录功能"，而是"测产线员工扫码后能否在3秒内加载工单" |
| 是否覆盖端到端业务流 | 不是单接口测试，而是从"触发→处理→结果→下游影响"全链路 |
| 是否有验收标准 | 通过/失败的标准是否量化、可测量 |
| 是否覆盖了业务异常路径 | 业务上的"非正常流程"（如物料不足、设备离线、超时未操作） |

### 维度2：测试分层策略 🟠 P1

| 检查项 | 说明 |
|--------|------|
| 是否区分了单元/集成/E2E层级 | 每层测试的目标是否清晰 |
| 测试金字塔比例是否合理 | E2E太多→维护成本高；单元太少→底层质量不可控 |
| 是否过度依赖UI测试 | UI测试脆弱，关键业务逻辑应有下层测试覆盖 |
| 冒烟测试/回归测试/全量测试是否有区分 | 不同场景用不同的测试集 |

### 维度3：数据准备与隔离 🟠 P1

| 检查项 | 说明 |
|--------|------|
| 测试数据是否可重复生成 | 不是"依赖生产数据"或"手搓数据" |
| 测试环境是否隔离 | 测试数据是否污染生产/预发布 |
| 是否有数据清理机制 | 测试结束后，脏数据是否清理 |
| 边界数据是否覆盖 | 空值、最大值、特殊字符、超长文本 |

### 维度4：异常与容错 🟠 P1

| 检查项 | 说明 |
|--------|------|
| 外部依赖不可用时系统表现 | 数据库断连、第三方API超时、消息队列积压 |
| 输入异常是否覆盖 | 非法格式、越界值、SQL注入尝试、XSS尝试 |
| 系统内部异常是否覆盖 | OOM、磁盘满、网络抖动、并发冲突 |
| 是否有幂等性验证 | 同一请求重复提交是否产生重复数据 |

### 维度5：并发与一致性 🔴 P0（MES/产线系统必查）

| 检查项 | 说明 |
|--------|------|
| 多人同时操作同一资源 | 两名操作员同时扫码同一设备 |
| 数据竞争条件 | 读-改-写非原子操作是否导致数据不一致 |
| 超时与锁机制 | 分布式锁是否有效，超时释放是否正常 |
| 最终一致性验证 | 异步场景下数据最终是否一致 |

### 维度6：状态机与流转 🟠 P1

| 检查项 | 说明 |
|--------|------|
| 是否覆盖所有状态转换路径 | 从状态A→B→C→D的所有合法路径 |
| 是否覆盖非法状态转换 | 从状态A直接跳到D是否被阻止 |
| 状态回退是否验证 | 撤回/驳回/反审核场景 |
| 并发状态变更 | 同一单据在不同终端同时操作 |

### 维度7：配置与参数化 🟡 P2

| 检查项 | 说明 |
|--------|------|
| 业务规则是否可配置测试 | 配置项变更后测试能否自动适应 |
| 环境差异是否纳入测试 | 开发/测试/预发布/生产环境的配置差异 |
| 参数边界是否覆盖 | 最小值、最大值、临界值 |

### 维度8：安全基线 🟡 P2

| 检查项 | 说明 |
|--------|------|
| 权限控制是否验证 | 无权限用户能否访问/操作 |
| 敏感数据是否脱敏 | 日志/响应中是否泄露密码、token、个人信息 |
| 接口防重放/防篡改 | 是否有签名验证、token防重放 |

### 维度9：性能基线 🟡 P2

| 检查项 | 说明 |
|--------|------|
| 是否有性能基线 | 响应时间、吞吐量、并发量的基准值 |
| 是否覆盖峰值场景 | 换班高峰期、月末结算、批量导入 |
| 资源泄漏是否检查 | 内存/连接池/线程池是否泄漏 |

### 维度10：可观测性 🟡 P2

| 检查项 | 说明 |
|--------|------|
| 关键操作是否有日志输出 | 测试时能否通过日志定位问题 |
| 日志是否包含足够上下文 | 请求ID、用户ID、操作时间、入参 |
| 告警是否触发 | 异常场景下告警通道是否正常工作 |

### 维度11：回归与自动化 🟠 P1

| 检查项 | 说明 |
|--------|------|
| 核心场景是否有自动化回归 | 不是每次发版都手工跑一遍 |
| 自动化用例维护成本是否可控 | 页面变更是否导致大量用例失效 |
| 是否区分冒烟/回归/全量 | CI流水线中是否分级执行 |

### 维度12：文档与可追溯性 🟡 P2

| 检查项 | 说明 |
|--------|------|
| 测试用例是否关联需求 | 每个用例能否追溯到PRD中的具体需求 |
| 测试结果是否可追溯 | 失败用例能否快速定位到问题根因 |
| 测试报告是否结构化 | 是否包含：测试范围、通过率、遗留问题、风险项 |

### 维度13：环境与依赖 🟡 P2

| 检查项 | 说明 |
|--------|------|
| 测试环境是否与生产环境一致 | 硬件/网络/中间件版本/配置差异 |
| 外部依赖是否mock | 第三方系统/硬件设备不可用时，测试是否可独立运行 |
| 环境准备时间是否可控 | 搭建一个新测试环境需要多久 |

### 维度14：上线与回滚 🟠 P1

| 检查项 | 说明 |
|--------|------|
| 上线前是否有验收测试 | 预发布环境是否完整跑通 |
| 回滚方案是否经过测试 | 回滚后数据是否一致，业务是否可恢复 |
| 灰度策略是否验证 | 灰度比例、灰度切换、灰度回退 |

## 审查流程

### Step 1：理解上下文
先搞清楚：
- 要测的是什么系统？（MES/IES/IPS/ALink…）
- 业务场景是什么？（产线操作/后台管理/报表查看…）
- 测试的阶段？（用例评审/方案评审/结果验收）
- 测试用例的输入来源？（PRD/设计文档/已有用例集）

### Step 2：逐维审查
按P0→P1→P2顺序执行14维检查。
每检查完一个维度，输出：
- ✅ 通过（无问题）
- ⚠️ 建议（有优化空间，非硬伤）
- ❌ 问题（必须修复）

### Step 3：汇总输出
输出结构：
```
## 📋 审查结论
整体评价：[优秀/合格/待改进/不合格]

## 🔴 必须修复（P0）
- 问题1：... 建议：...
- 问题2：... 建议：...

## 🟠 建议优化（P1）
- 建议1：... 理由：...

## 🟡 可进一步提升（P2）
- 建议1：... 理由：...

## ✅ 已覆盖亮点
- 亮点1：...
```

### Step 4：输出文档
审查结果输出为飞书云文档，关联到对应项目。

## 附录A：BPTest vs 传统测试用例的区别

| 维度 | 传统测试用例 | BPTest用例 (BP视角) |
|------|---------|----------------|
| 用例粒度 | 功能点/接口/页面 | 业务流程/业务场景 |
| 关注点 | "功能是否跑通" | "业务价值是否实现" |
| 用例设计方法 | 等价类/边界值/正交 | 业务流/异常流/风险场景 |
| 验收标准 | 通过率>99% | 业务风险是否可控 |
| 输出物 | 测试报告 | 业务风险评估报告 |

## 附录B：快速检查清单（6个核心问题）

当用户说"帮我quick看一下这个测试用例"时，只看这6个：

1. ❓ 测试是否覆盖了端到端业务流？（不只是单接口/单页面）
2. ❓ 异常场景是否覆盖？（依赖挂、数据错、操作错）
3. ❓ 并发场景是否考虑？（产线系统必查）
4. ❓ 测试数据是否可重复、可清理？
5. ❓ 核心场景是否有自动化回归？
6. ❓ 上线/回滚方案是否经过验证？

## 附录C：BP测试思维三问

审查任何测试用例前，先问自己这三个问题：

1. **业务视角**：如果我是产线操作员/业务用户，这个测试能保证我不出问题吗？
2. **风险视角**：最坏情况下系统出什么问题？这个测试能发现吗？
3. **成本视角**：这个测试的成本（人力/时间/环境）是否与业务风险匹配？

> **核心信条**：测试不是为了证明系统没问题，而是为了发现系统在真实业务场景下可能出什么问题。
